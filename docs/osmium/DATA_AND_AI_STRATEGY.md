# OSMIUM data and AI strategy

## 1. Position

Trust comes from **continuity, provenance and consent**. The athlete's logged history is the product's primary asset. AI is an interpreter on top of it, not a source of truth.

## 2. Four provenance classes (never mixed)

Every stored datum and every sentence the coach says belongs to exactly one class. The class is carried in data, not inferred later.

| Class | Definition | Examples (today → target) | Mutable? | UI treatment |
|---|---|---|---|---|
| **1. Logged fact** | Something the athlete did, recorded at the time | `SetLog` (weight, reps, completed, createdAt), session `completedAt` | **No.** Corrections are new records referencing the original | Plain numerals (data typography) |
| **2. Self-report** | A subjective observation entered by the athlete | Set RPE, session RPE, limitation before/after, notes, *new*: fatigue, energy, soreness, sleep hours/quality, pain | Editable by the athlete, with history kept | Labelled "you reported" |
| **3. Derived** | Deterministically computed from 1+2 by code with a known method | `ExerciseProgressionState`, `TrainingState`, PRs, volume, adherence, every `ProgressionDecision.reason` | Recomputed, never hand-edited | Labelled "calculated from N sessions". Shows **insufficient data** below its minimum input |
| **4. AI hypothesis** | Generated by a model | Coach message text, proposed adaptations | Never becomes 1–3 without an explicit approval event | Labelled as a suggestion. Proposals need APPLY |

### Today's state (verified)

Classes 1–3 exist but are **not tagged**. Class 4 exists only as `DemoCoachProvider` output, which is rule-based rather than AI, but the treatment is the same. Mixing that already happens:

- `WorkoutExercise.recommendationReason` (derived) is overwritten with `"Reduced by Coach for today only."` when an adaptation applies (`adaptation.ts`), which blends classes 3 and 4 in one field. **Target:** keep the engine's reason and attach an `adaptationId`.
- (Fixed 4 Nov, defect D2.) `ExerciseProgressionState.lastLoad` used to store a *recommendation* (derived) where the seed stores the *performed* load (logged fact). This is defect D2.

## 3. Athlete memory model

"Memory" means structured, editable records the athlete can see. It does not mean embeddings or opaque summaries.

| Memory | Store | Who writes | Athlete can |
|---|---|---|---|
| Profile, goals, preferences, dislikes | `AthleteProfile` | Athlete | Edit |
| Limitations | `AthleteLimitation[]` + check-in pain series | Athlete; coach *proposes* `FLAG_LIMITATION` | Edit, deactivate |
| Training context (gym/home, equipment, time) | `TrainingContext` | Athlete | Edit |
| History | `WorkoutSession[]` (append only) | App on finish | View, annotate, export |
| Recovery | `RecoveryCheckIn[]` | Athlete | Edit, delete |
| Decision provenance | `AdaptationRecord[]`, `generationExplanation` snapshot per session | App | View |
| Coach transcript | `CoachMessage[]` (new persistence) | App | View, delete |

The coach context is **assembled from these records** at request time, filtered to the minimum the request needs. It is not a long free-text "memory" that the model rewrites.

## 4. AI Coach contract

### 4.1 What the model may do
- Interpret free text ("my shoulder's cooked, only have 35 minutes").
- Explain existing engine decisions using the engine's own `reason` strings.
- Propose **one** adaptation from the closed union: `SHORTEN_DURATION | REMOVE_MOVEMENT_PATTERN | INCREASE_CARDIO | SUBSTITUTE_EXERCISE | FLAG_LIMITATION | EASIER | HARDER` (extend the union deliberately, e.g. `SWITCH_LOCATION`, with an engine path and tests first).

### 4.2 What the model may never do
- Output loads, set counts or rep targets as numbers to apply. The engine computes those.
- Apply anything. There is no server-side mutation of training data from model output.
- Diagnose, or imply medical clearance. Pain always routes to `FLAG_LIMITATION` plus a "seek a qualified professional" line (already in `DemoCoachProvider`).
- Invent history ("last week you did…") that is not in the assembled context. The system prompt includes the provenance-tagged context and an instruction to say "I don't have that logged" when something is missing.

### 4.3 Validation
- Server: parse the model JSON against a schema (zod is already a transitive dependency; add it directly in the Edge Function). On failure, return `{ message }` with no proposal.
- Client: `RemoteCoachProvider` re-validates `proposedAdaptation.type` against the union before the UI may show APPLY.
- Tests: a fixture suite of model outputs (valid, malformed, out-of-union, load-injection attempts) → only valid typed proposals survive.

### 4.4 Prompt-injection posture
Athlete-entered notes are **data** in the prompt, delimited and labelled. The model's tool surface is the proposal union, nothing else. Because every proposal still needs a human tap, the blast radius of an injection is limited to a wrong suggestion.

### 4.5 Provider and model
Use a server-side Claude model via the Edge Function. Pick the model and parameters in step 8 against cost and latency measured on real transcripts. Keep the provider behind `CoachProvider` so it can be swapped without UI changes.

## 5. Recovery, honestly

- Inputs are self-report only (class 2) until a wearable integration exists, which is post-launch.
- **No readiness percentage.** A derived readiness indicator may be introduced only if (a) its formula is documented here, (b) the UI shows its inputs, and (c) it shows "insufficient data" below a minimum number of check-ins. v2: *"Only display calculated percentages when inputs and method exist."*
- How recovery affects training is conservative and engine-side: e.g. high fatigue or pain → target RPE 6 (this mirrors the existing `buildTargetRPE` rule for limitations) and a coach-proposed shorten. It never auto-applies.

## 6. Persistence migration and storage keys

- **Keep `vynkaer.*` AsyncStorage keys.** They are not user-visible. Renaming them needs a migration that can lose data for no product benefit. Add `osmium.schemaVersion` as the first OSMIUM key and run migrations keyed on it.
- **D1 fixed (4 Nov):** distinguish *missing* (seed allowed, first launch only) from *unreadable* (never seed; keep the raw value under a quarantine key and surface an error state).
- Mark seed data explicitly: add `isDemo: true` to seeded sessions and profile in the migration, so demo data can never be confused with real logs once accounts exist, and is excluded from sync.

## 7. Privacy

| Requirement | Plan |
|---|---|
| Data minimisation | Coach context assembled per request; send no notes or pain detail unless the request needs them |
| Consent | Explicit opt-in before any data leaves the device (sync, coach). `ConsentControl` component (v2) |
| Export / deletion | Edge Functions (step 11); local "delete all data" alongside the existing Reset demo data |
| Sensitive data | Pain, sleep and fatigue are health-adjacent. Treat them as sensitive: encrypted in transit, RLS-isolated, excluded from analytics, retained only while the account exists |
| Model provider | Use the provider's zero-retention / no-training options where available. Document this in the privacy policy |
| Repo | No real athlete data or credentials committed. Seed stays synthetic |
